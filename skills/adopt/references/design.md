# 1~2단계 — 분석 항목과 설계 항목

## 분석 — 무엇을 어디서 보나

출처를 같이 적는다(파일:줄 또는 명령). 못 찾으면 「없음」, 짐작이면 「추정」.

| 항목 | 볼 곳 |
| --- | --- |
| 스택·언어·런타임 버전 | `package.json`·`pyproject.toml`·`go.mod`·`Cargo.toml`·`*.csproj`·`Gemfile`·`.nvmrc`·`.tool-versions`·Dockerfile |
| 패키지 매니저·워크스페이스 | lock 파일, `workspaces`, `pnpm-workspace.yaml`, 모노레포 폴더 |
| 실행·빌드·테스트·린트 명령 | `package.json` scripts, `Makefile`, `justfile`, `Taskfile`, `.github/workflows/*`, README 의 「개발」 절 |
| 테스트 계층과 소요 | 단위·통합·e2e 구분(폴더·설정 이름), CI 잡 순서, 느린 표시(`e2e`·`integration`) |
| 사용자 실행 경로 | 배포 방식(웹 배포·CLI 전역 설치·앱 패키징·라이브러리 배포·Docker), README 설치 절 |
| 로컬 데이터·런타임 자원 | `.env*`(값은 읽지 말고 키만), DB 파일·docker-compose 서비스·포트·소켓·사용자 설정 경로 |
| 외부 의존 | 외부 API·SaaS·CLI 호출, 버전 민감 라이브러리 |
| 브랜치·PR 관례 | 기본 브랜치(`git symbolic-ref refs/remotes/origin/HEAD`), 최근 브랜치 이름 꼴(`git branch -r`), 일감 ID 꼴, PR 템플릿 |
| 일감 트래커 | 브랜치·커밋의 ID 접두, 이슈 링크, MCP·CLI(gh 등) 사용 흔적. 사용자에게 확인 |
| 에이전트 도구 | 지침 파일 종류(Claude Code·Codex·Cursor…), 사용자가 쓰는 도구 — 확인 |
| 터미널 제어 도구 | `command -v corral tmux` · 사용자가 쓰는 것 확인 |
| git 훅 | `git config core.hooksPath`, `.husky/`·`.githooks/`·`.git/hooks/` 의 실행 파일, `command -v gitleaks` — paddock pre-commit 은 gitleaks 가 없으면 모든 커밋을 막는다 |

## 설계 항목

### 모듈과 harness

| 결정 | 기본 | 다르게 할 근거 |
| --- | --- | --- |
| `l1` | 켬 | 사용자가 흐름 없이 L0 만 원함, 또는 산출물 레포를 둘 수 없음(`specs-inrepo` 미구현) |
| `specs-repo` | `l1` 과 같이 켬 | — (v0 에서 l1 은 specs-repo 를 전제) |
| `l2` + `PADDOCK_HARNESS` | 켬(`l1` 을 켤 때만 — l1 을 끄면 l2 도 끈다). `corral` 이 설치돼 있고 사용자가 쓰면 corral, 아니면 bare | 터미널 제어 없이 쓰겠다 → l2 끔(그러면 task 흐름의 워커 기동·완료 감지가 전부 공백이 된다고 알린다) |
| `bundle` | 끔 | 서로 의존하는 작업 묶음을 feature 브랜치로 모으는 관례가 있음 |
| `l3` | 끔 | release 자산이 v0 에 없다 — 켜면 출고를 가리키는 문장만 남는다. 출고 흐름이 이미 있고 그 문서를 가리키고 싶을 때만 |

### 변수 (`assets/README.md` 「변수」 표 전부 채운다)

| 변수 | 정하는 법 |
| --- | --- |
| `PROJECT_NAME` | 레포 이름 또는 README 제목 |
| `BASE_BRANCH` | 원격 HEAD 브랜치 |
| `WORKTREE_DIR` | 기존 관례가 있으면 그것, 없으면 `.claude/worktrees` |
| `ISSUE_PREFIX` | 트래커 ID 접두. 트래커가 없으면 빈 값(슬러그만 쓰는 모드) |
| `SPECS_ROOT` | 산출물 레포 위치 — 본체 옆 형제 폴더 권장: `<본체>/../<레포>-specs` |
| `BUNDLE_PREFIX` | `feature/` (bundle 을 켤 때만 의미) |
| `MAX_FIX_ROUNDS` | 3 |
| `VARIANT_SUFFIXES` | 구현을 맡길 도구마다 `-<도구>`. 예: `-claude -codex` |
| `PR_FOOTER` | 레포·사용자의 PR 서명 관례가 있으면 그것, 없으면 빈 값 |

### 설계 슬롯 — 무엇을 써야 하나

각 슬롯은 짧게(대개 3~10줄). 명령은 출처가 있는 실제 명령만.

| ID | 쓸 것 | 좋은 예 | 피할 것 |
| --- | --- | --- | --- |
| D1 | 무엇을 만드는가, 스택, 방향 문서 위치 (2~4줄) | 「X 를 위한 Y 앱. Next.js 15 + Prisma. 방향은 docs/vision.md」 | 폴더 트리 전체, 설치 방법 |
| D3 | 일감 읽는 법·상태 전이 법·상태 이름. 트래커 없으면 「사용자 지시 원문을 00-analysis 첫 줄에 붙인다, 전이 없음」 | 「`gh issue view N`; 라벨 `in-progress`→`review`→close」 | 쓰지 않는 상태까지 나열 |
| D5 | 네이티브 실행 = 사용자가 실제로 쓰는 경로에서 1회. 격리 실행과 무엇이 다른가 | 웹: 「`pnpm build && pnpm start` 의 프로덕션 빌드를 브라우저로」 · CLI: 「`npm i -g .` 뒤 전역 명령으로」 · 라이브러리: 「pack 한 tarball 을 빈 프로젝트에 설치해 import」 | 단위 테스트를 네이티브로 부르기 |
| D6 | 건드리지 말 사용자 자원, 동시에 하나만 쓸 자원, 커밋하지 않을 사본 | 「로컬 개발 DB(`docker compose` 의 db) — 시험은 별도 DB 이름으로」 | 값(비밀) 적기 |
| D7 | 빠른 확인(수 분) vs 최종 관문 명령 | 「빠른: `pnpm test:unit`, `pnpm lint` · 최종: `pnpm test:e2e` + D5」 | 없는 스크립트 |
| D8 | 경량으로 다룰 닫힌 범주 목록 + 「전체로 올리는 것」 프로젝트 줄 | 「경량: 문서·카피 문구·스타일 상수 / 전체: 마이그레이션·인증·결제」 | 목록을 넓게 — 애매하면 전체 |
| D9 | 일감 관문 스크립트를 무엇으로 쓰고 worktree 경로를 어떻게 받나 | 「node 스크립트, 첫 인자 = worktree 절대경로, 그 안의 node_modules 를 쓴다」 | — |
| D12 | 이 프로젝트에서 리뷰어가 특히 볼 것, 외부 사실 대조 대상 | 「권한 검사 누락, N+1 쿼리, 공개 API 호환성 / Stripe API 버전」 | 일반론(가독성 등) |
| D13 | 외부 서치를 맡길 도구·조건. 없으면 「없음 — 코디가 직접 검색」 | — | — |
| D15 | 사용자가 통합 결과를 직접 실행해 보는 한 줄 | 「`pnpm dev` 후 localhost:3000」 | — |
| D16 | 머지 뒤 단계 — 무엇이 바뀌면 무엇을 하나(빌드 게이트, 머지로 도는 CI·배포와 확인법, 수동 배포·마이그레이션 순서, 라이브 확인, 프로젝트 함정), 단계마다 트리거(머지로 자동 / 사람이 실행)와 되돌릴 수 없음 표시. 기존 마무리·배포 스킬이 있으면 그 단계를 옮긴다 | 「api 바뀌면: CI deploy 런 성공 확인 → 컨테이너 새 이미지·기동 로그 (머지 = 운영 배포)」 | 「배포 확인」처럼 명령·확인 근거 없는 문장 |

### `.agents/defaults.md` (seed — 파일째 쓴다)

「역할 기본값」 표: 본체 · 코디네이터(판정) · 구현 · 리뷰어 ① (· 리뷰어 ②, 경쟁 구현은 쓸 때만) · 서브에이전트.
칸: 도구 · 모델(전체 식별자) · effort · advisor.
- 사용자에게 쓰는 도구·구독을 묻고, 모르면 「구현과 리뷰어는 다른 모델」「리뷰어는 구현자와 다른 세션」 원칙만 지켜 제안한다.
- 모델 식별자는 사용자가 확인한 것만 적는다 — 짐작한 식별자를 적지 않는다. 확인 전이면 칸에 「확인 필요」를 붙인다.
- **지정 리뷰어(①)·경쟁 상대 후보는 계정 카탈로그로 대조한다** — 방법은 `${CLAUDE_PLUGIN_ROOT}/assets/l1/.agents/agent-tools.md` 의 그 도구 절.
  「없음」이면 그 모델을 지정 리뷰어로 제안하지 않는다 — 게이트 보고에 카탈로그 원문 요지와 대안 구성(다른 도구를 ①로, 또는 그 도구 행을 「일시 중지」)을 낸다.
  「있음」은 미보증이다(갱신 실패 낙하는 걸렀지만 거절은 첫 라운드 기동 확인에서야 잡힌다) — 보고에 그렇게 적는다.
  사용량은 세션을 띄우지 않는 명령이 있는 도구만 보고, 이미 90% 이상이면 함께 적는다. 「확인 실패」(그 도구 절이 없거나 출력이 빔)면 「확인 필요」 그대로 두고 그 사실을 적는다.
  이 확인 명령은 도구 캐시를 갱신할 수 있지만 대상 레포·사용자 설정 파일에는 쓰지 않는다 — 게이트 전 쓰기 0 과 맞는다.
  도구 설정 파일의 기본 모델(예: Codex `config.toml` 의 `model`)은 사용자가 평소 쓰는 값의 힌트일 뿐 계정에서 쓸 수 있다는 근거가 아니다.
- 출처는 대상 레포와 사용자 답뿐이다. 같은 기계의 다른 레포(다른 프로젝트의 `defaults.md` 등)·홈 설정에서 값을 베껴 오지 않는다 — 참고했으면 「제안」이라고 출처를 밝히고 「확인 필요」로 둔다.
- 「선택 근거」 절에 역할마다 한 줄.

### 옮기는 계획

0단계 4분류 결과를 「출처(파일·절) → 목적지(파일·슬롯) · 처리(옮김/요약해 옮김/버림-중복/그대로)」 표로.
`paddock-render apply --dry-run` 이 낸 충돌 파일이 전부 이 표에 있어야 하고, **충돌 파일은 덩어리 전수** — 원본의 모든 절·불릿 묶음이 한 행씩 있어야 한다.
「버림-중복」 행은 겹치는 고정 문장의 위치(파일·절)를 근거 칸에 적는다. 「요약해 옮김」은 요약에서 빠지는 원문이 다른 행으로 가는지 본다.
기존 훅(`core.hooksPath`·husky)이 있으면 처리(유지·합침·교체)를 이 표에 넣는다 — 기본은 덮지 않고 승인 게이트에서 묻는다.
