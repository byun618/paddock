# task-start — 작업 시작 (본체 세션에서)

<!-- paddock:module bundle -->
묶음 자식은 그 체크포인트의 묶음 코디가 이 스킬로 시작한다.
<!-- /paddock:module -->

**이 문서에는 도구 명령이 없다.** 능력 이름은 겹낫표로 감싸 적고, 명령은 **`.agents/harness/capabilities.md`**
(하네스 능력 계약)의 「매핑 선택」으로 고른 도구별 매핑에서 읽는다. 어느 매핑을 골랐는지는 `00-start.md` 에 기록한다.

## 코디네이터 선택

- 신규 작업은 사용자가 지정한 코디네이터 도구를 사용한다. 선택할 수 있는 도구 집합과 미지정 기본값은
  `.agents/defaults.md` 의 역할 기본값에 있다. 이 선택은 해당 작업에만 적용한다. 현재 대화 도구나 전역
  기본 모델로 추측해 바꾸지 않는다.
- 기존 작업은 `{{SPECS_ROOT}}/{{TASK_NAME}}/00-start.md`(절대경로, AGENTS.md 「산출물 규칙」)를 먼저 읽는다. 미지정 재개는 기록된
  코디네이터를 따른다. 기록이 없는 과거 작업은 킥오프·실제 세션을 확인해 기록부터 보완한다.
- 선택이 기존 기록과 다르거나 `.agents/defaults.md` 의 역할 기본값에 없는 도구를 요청하면 새 터미널을 만들지 않는다 — 도중 교체는
  이 스킬 밖이다. 기존 코디네이터·워커·Run과 미완 작업을 확인하고 인계 범위를 사용자와 정한 뒤 진행한다.
  동시에 두 코디네이터를 만들지 않는다.
- 코디네이터 선택과 워커·리뷰어 구성은 별개다. 신규 기본은 **단독 구현 → 코드 리뷰**이고 역할별
  모델·effort·리뷰어 구성은 [기본 구성](../../defaults.md)(`.agents/defaults.md`)에 있다(task-coordinate §4–5).
  설계는 별도 단계가 아니라 구현 워커가 흡수한다.
  신규 작업은 기본 구성을 설정 질문 없이 적용하고 명시한 변경만 덮어쓴다.
  기존 작업 재개는 기록된 구성을 유지한다. 사용자 변경 지시는 예외 범위와 함께 기록한다.

## 절차

1. **일감·환경 확인**: 일감을 읽는다 — 방법은 아래 D3.
<!-- paddock:design D3 -->
<!-- adopt 가 쓴다: 이 프로젝트의 트래커에서 일감 본문을 읽는 방법(예: MCP 도구 이름·`gh issue view`·`linear` CLI). 트래커가 없으면 "일감 본문은 사용자가 준 설명을 쓰고, 일감 ID 대신 슬러그를 ID 로 쓴다" 로 채우고 이 줄을 단순화한다 -->
<!-- /paddock:design -->
   `git status`·`git worktree list`로 본체 {{BASE_BRANCH}}와 기존 작업을 확인하고, 선택한 코디네이터 도구가 실제로
   실행 가능한지 확인한 뒤 **하네스 매핑을 고르고 그 매핑의 『전제 점검』을 실행한다**.
<!-- paddock:module bundle -->
   묶음 코디가 feature worktree 에서 이 단계를 하면 2단계 블록의 `ROOT=…` 줄을 먼저 실행하고 `git -C "$ROOT" status` 로 본체를 본다.
<!-- /paddock:module -->
   제어 런타임이 꺼져 있거나 일감 트래커를 읽을 수 없으면 이 단계에서 원인을 보고한다. 다른 도구로 몰래 대체하지 않는다.
   **『전제 점검』이 불일치를 내면 멈춘다** — 매핑이 요구하는 능력을 런타임이 광고하지 않으면 추측으로
   진행하지 않는다. 광고를 대조할 수 없는 도구는 그 사실을 기록하고 판정표의 공백으로 낸다.
   레포 미등록처럼 사용자 승인으로 풀리는 전제는 매핑이 적은 명령을 보여 승인을 받고, 실행한 뒤 점검을 다시 돈다.
   **제어 런타임을 띄울 때의 환경 조건(상속되면 배달 판정이 무력화되는 env 마커 등)은 매핑의
   『전제 점검』에 적혀 있다** — 런타임을 새로 띄우는 경우 그 조건을 먼저 읽는다.
   코드 레포의 `git config core.hooksPath` 가 `.githooks` 인지(새 클론이면 비어 있다 — 설정한다), `gitleaks` 가 PATH 에 있는지 확인한다.
   없으면 훅이 모든 커밋을 막는다.
<!-- paddock:module specs-repo -->
   **산출물 레포**(`{{SPECS_ROOT}}`, 본체 옆 폴더, AGENTS.md 「산출물 규칙」)가 있는지, 그 레포의 `core.hooksPath` 도 `.githooks` 인지 같이 확인한다.
<!-- /paddock:module -->
   슬러그는 타이틀에서 케밥케이스 1~3단어로 파생하며, 기존 작업의 슬러그는 재사용한다.
2. **분기 기준 선택 → 작업 worktree 생성** (신규만, 본체는 {{BASE_BRANCH}} 유지):
   - **독립 작업**(기본): `{{BASE_BRANCH}}` 에서 딴다. 게이트 ② 에서 {{BASE_BRANCH}} 대상 PR 이 된다.
<!-- paddock:module bundle -->
   - **묶음 자식**: 서로 의존하는 작업 묶음(체크포인트)이면 `{{BUNDLE_PREFIX}}{{BUNDLE_NAME}}`(체크포인트 작업 이름)에서 딴다.
     **묶음 자식의 task-start 는 그 묶음의 묶음 코디가 한다** — 본체가 자식 시작 요청을 받으면 직접 하지 않는다:
     활성 묶음 코디가 있으면 그 세션에 넘기고(통로는 묶음 코디 절차 4), feature 는 있는데 묶음 코디가 없으면 아래 「체크포인트 시작」으로 묶음 코디부터 띄운다.
     feature 가 아직 없으면 사용자에게 묶음으로 열지 한 번 묻고, 열면 「체크포인트 시작」으로 연다.
     게이트 ② 에서 PR 대신 feature 로 로컬 merge 된다(AGENTS.md 「브랜치 규약」). 미지정·애매하면 독립 작업이다 —
     트래커 부모가 체크포인트라는 것만으로 묶음 자식이 되지 않는다(판단 기준은 의존이다).
   - **체크포인트 시작**(묶음 열기): 체크포인트 일감 자체를 시작하면 이 경로다(분해 뒤 자식이 하나뿐이면 묶음 코디 절차 2 가 접는다). 작업 브랜치 `{{BUNDLE_NAME}}` 를 만들지 않는다. `origin/{{BASE_BRANCH}}` 최신에서 feature 를 만들어 origin 에 push 하고,
     feature worktree 를 그 feature 체크아웃으로 연다 — 이 worktree 가 **묶음 코디**의 작업 worktree 다. 만료일(기본 시작일 + 2주)을 00-start 에 적는다.
     feature 가 이미 있으면(묶음 코디 없이 자식만 시작된 경우, PR 을 연 뒤 수정하려고 정리된 feature worktree 를 다시 여는 경우 — 묶음 코디 절차 6) 만들기·push 는 건너뛰고 feature worktree 와 묶음 코디만 연다.
     **본체가 이미 분해·자식 시작을 했어도 묶음 코디는 띄운다** — 00-start 분해 상태는 3단계.
     묶음 코디가 하는 일은 [묶음 코디 절차](../task-coordinate/references/bundle.md)가 원본이다.
   ```bash
   git fetch origin {{BASE_BRANCH}} && git branch --no-track {{BUNDLE_PREFIX}}{{BUNDLE_NAME}} origin/{{BASE_BRANCH}} && git push -u origin {{BUNDLE_PREFIX}}{{BUNDLE_NAME}}    # 체크포인트 시작 — feature 가 없을 때만
   ```
<!-- /paddock:module -->
   worktree 는 **본체 기준 절대경로**로 만든다 — worktree 안에서 쳐도 상대경로처럼 그 아래로 중첩되지 않는다(AGENTS.md 「중첩 금지」).
   `ROOT` 는 어느 worktree 에서 쳐도 본체 checkout 을 가리킨다.
   ```bash
   ROOT="$(dirname "$(git rev-parse --path-format=absolute --git-common-dir)")"
<!-- paddock:module bundle -->
   git fetch origin {{BUNDLE_PREFIX}}{{BUNDLE_NAME}}    # 묶음 자식만 — 분기 전에 origin/feature 를 최신으로. 실패하면 분기하지 않고 멈춘다(독립 작업·체크포인트 시작은 건너뛴다)
   git worktree add "$ROOT/{{WORKTREE_DIR}}/{{TASK_NAME}}" -b {{TASK_NAME}} origin/{{BUNDLE_PREFIX}}{{BUNDLE_NAME}}   # 묶음 자식
   git worktree add "$ROOT/{{WORKTREE_DIR}}/{{BUNDLE_NAME}}" {{BUNDLE_PREFIX}}{{BUNDLE_NAME}}                                       # 체크포인트 시작 — feature worktree
<!-- /paddock:module -->
   git worktree add "$ROOT/{{WORKTREE_DIR}}/{{TASK_NAME}}" -b {{TASK_NAME}} {{BASE_BRANCH}}   # 독립 작업
   ```
<!-- paddock:module bundle -->
   **묶음 자식이면 생성 직후 상위를 feature worktree 로 지정한다** — 사이드바가 체크포인트 아래에 중첩해 보이게 하는
   표시용 메타다. feature worktree(`{{WORKTREE_DIR}}/{{BUNDLE_NAME}}`)가 있을 때만 하고,
   명령은 매핑의 「git 으로 만든 직후 상위를 지정한다」 줄을 따른다. **실패는 경고만** — 거절 원문을
   00-start 에 남기고 진행한다. 독립 작업은 루트로 둔다. 그 능력이 없는 매핑이면 이 단계는 공백이다.
<!-- /paddock:module -->
   재개는 기존 worktree와 코디네이터 터미널을 확인한다. 활성 코디네이터가 있으면 그 세션으로
   이어가며 새로 만들지 않는다. 세션이 없을 때만 기록된 도구로 재기동한다.
<!-- paddock:module bundle -->
   묶음 코디도 같다(묶음 코디 절차 머리) —
   정리를 마쳐 작업 worktree 가 사라진 묶음 코디 세션은 활성으로 세지 않는다(묶음 코디 절차 6).
<!-- /paddock:module -->
3. **기동 전에 선택 기록**: `{{SPECS_ROOT}}/{{TASK_NAME}}/00-start.md`를 작성한다.
<!-- paddock:module specs-repo -->
   산출물 레포에 그 폴더만 커밋·push 한다(AGENTS.md 「산출물 규칙」의 커밋 명령). 작업 worktree 에는 산출물을 두지 않는다.
<!-- /paddock:module -->
   최소 항목: {{TASK_REF}}, 슬러그, 작업 브랜치·**분기 기준**·절대 worktree 경로,
   **산출물 작업 폴더 절대경로**(코디·워커·리뷰어가 이 값을 그대로 쓴다), 코디네이터 도구, 선택 근거
   (사용자 지정/신규 기본값/재개), 모델·effort(미지정 기본값은 `.agents/defaults.md` 의 역할 기본값),
   **선택한 매핑**, 기동 상태. 지정 모델을 쓸 수 있는지 기동 전에 확인하고(방법은 `.agents/agent-tools.md` 의 그 도구 절,
   규칙은 `.agents/defaults.rules.md` 「리뷰어 사용 불가 시 자동 전환」), 쓸 수 없으면 같은 파일 「운영 규칙」대로 보고한다.
   확인 결과(도구마다 카탈로그 있음/없음/확인 실패 · 사용률)를 한 줄로 적는다 — 리뷰 구성이 바뀔지 사용자가 게이트 ⓪ 전에 안다.
   모든 역할의 요청 모델·effort·advisor·단독/경쟁 방식은 `.agents/defaults.md` 에서 복사한다.
   처음 상태는 `기동 전`.
<!-- paddock:module bundle -->
   분기 기준은 `{{BASE_BRANCH}}` 이거나 feature 브랜치와 그 만료일이다.
<!-- /paddock:module -->
   워커 구성·구현→리뷰 흐름·사용자 예외(경량/전체 경로 지정 포함), 수정 라운드용 워커 유지 요청도 기록하고, 재개는 이력을 덧붙인다.
<!-- paddock:module bundle -->
   **체크포인트 시작이면** 체크포인트 폴더의 00-start 에 묶음 항목을 더한다: 묶음 표시(`묶음 코디 — {{BUNDLE_REF}}`, 작업 브랜치 대신 feature 브랜치·만료일),
   분해 상태(`분해 전` / `분해 끝` 둘 — `분해 끝` 은 누가 분해했든 다시 하지 않는다는 뜻), 이미 시작된 자식(따로 — 자식·그 코디 세션). 구현 워커·리뷰어 구성은 적지 않는다 — 묶음 코디는 그것을 띄우지 않는다(자식 코디 몫).
<!-- /paddock:module -->
   이 기록은 6단계 전달 전에 끝낸다.
4. **코디네이터 세션 기동** — 『세션 기동』. 작업 폴더는 3단계에 기록한 **절대경로**로 준다.

   선택은 3단계에 기록한 코디네이터 도구다. 모델·effort는 사용자 지정값, 미지정이면 3단계의 기본값을 **명령에
   명시한다**(이유는 AGENTS.md 「도구 역할」). advisor 지정이 그 매핑에서
   불가능하면 그 사실을 기록한다(조용히 빼지 않는다).
   반환된 세션 handle 을 확보하고 `00-start.md`에 기록한다. 응답이 세션 기록 경로를 돌려주면 그 경로도 같이 적는다
   (devlog 재료 — task-coordinate §8. 6단계의 전달 전 커밋에 들어간다). 기동 응답에 경로가 있는지는 도구마다 다르다
   — 매핑 『세션 기동』 절. 사용자에게 보여줄 코디네이터 세션에만
   포커스 전환을 쓴다(매핑에 따라 헤드리스에서는 미지원).
5. **상태 전이**: 트래커 상태를 forward-only 로 전이한다(트래커가 있으면) — 방법은 D3.
<!-- paddock:design D3 -->
<!-- adopt 가 쓴다: 시작 시 일감을 어느 상태로 어떻게 전이하는지(상태 이름·도구 호출), 상위 일감 계층이 있으면 그 규칙. 트래커가 없으면 "트래커가 없어 이 단계는 건너뛴다" -->
<!-- /paddock:design -->
   시작 세션이 전이를 요청한다. 코디네이터가 먼저 전진했다면 이미 전진했다는 응답(같은 상태·뒤로 가는 전이)을 존중한다.
<!-- paddock:module bundle -->
   부모가 체크포인트이면 부모도 함께 전이한다. 종료 때 부모 완료는 다른 미완
   자식이 없는지 확인한 뒤 판단한다 — task 하나 완료로 체크포인트 전체를 완료하지 않는다.
   체크포인트 시작이면 그 체크포인트 일감 자체를 전이한다.
<!-- /paddock:module -->
6. **준비 확인 후 킥오프 주입**:
   - 『준비 대기』로 지시를 받을 수 있는 상태인지 확인한다. **trust·로그인 화면이나 미검증 화면은
     사람이 치운다 — 제어 도구는 그 화면에 대답하지 않는다.** 타임아웃은 준비 완료가 아니며, 차단이었는지
     느렸을 뿐인지는 매핑이 지정한 근거 필드로 가른다. 『준비 대기』가 차단을 가리지 못하는 도구에서는
     주입 전에 『화면 관측』을 반드시 한 번 한다.
   - 준비가 확인되면 `00-start.md`의 상태를 `킥오프 전달 준비`로 갱신한다.
     **전달 기록의 커밋은 전달 *전*에 끝낸다** — 전달 뒤에 시작 세션이 커밋하면 이미 일을 시작한
     코디네이터의 미커밋 편집까지 쓸어 담고 인덱스 잠금으로 코디네이터 커밋이 실패한다.
     전달 후의 기록은 코디네이터가 맡는다.
   - 『본문 주입』으로 아래 지시를 **한 번만** 보낸다. **확인된 배달만 배달이고, 큐 수락·결과 불명은 중복 주입하지 않는다.**
   - 전달 뒤 배달 확인값(요청 id·일치 건수)·결과·시각을 작업 폴더의 **`delivery.md`** 에 이어 쓴다(시도마다 한 항목, 덮어쓰지 않는다). `00-start.md` 는 건드리지 않고 **커밋하지 않는다** —
     코디네이터가 다음 작업 폴더 커밋에 같이 넣는다. 배달 증명이 공백인 도구라면 그 사실과 사람이 화면으로 확인한 시각을 적는다.
     ```
     너는 {{TASK_REF}} 작업의 코디네이터야. <산출물 루트 절대경로>/{{TASK_NAME}}/00-start.md와
     .agents/skills/task-coordinate/SKILL.md를 읽고, 실제 세션에서 전제 도구를 확인한 뒤 절차대로 진행해.
     ```

     체크포인트 시작(묶음 코디)이면 이 지시를 대신 보낸다:

   - 전달 이후 이 파일·그 작업 폴더와 작업 브랜치는 코디네이터가 맡는다. 시작 세션은 `delivery.md` 말고 더 수정하지 않는다.
     실제 세션 점검 후 코디네이터가 `준비 완료` 또는 `차단 사유`를 기록한다.

## 기동 실패·재개

- **세션 생성 응답의 타임아웃은 실패가 아니라 지연일 수 있다.** 같은 worktree의 세션 목록에서 그 도구
  터미널을 먼저 찾고, 살아 있으면 그 handle을 기록해 재사용한다.
  확인 없이 재시도해 중복 코디네이터를 만들지 않는다. 남은 상태·다음 조치를 `00-start.md`에 남긴다.
- **`delivery.md` 가 없다고 미배달로 단정하지 않는다** — 주입 직후 세션이 끊겼을 수 있다. 코디네이터 세션이 살아 있으면 『화면 관측』이나 『세션 기록 오라클』로 먼저 보고, 도착이 보이면 그 사실을 `delivery.md` 에 적고 다시 주입하지 않는다.
- 포커스 전환 때문에 문제가 나면 포커스 없이 만든 뒤 별도로 전환한다.
- 화면 읽기·목록·본문 길이의 **수치 상한은 매핑에서 확인한다** — 줄 수와 바이트를 혼동하면 원자료가 잘린다.
- 시작 세션은 킥오프 전달 후 구현을 지휘하지 않는다. 이후 과정은 선택된 코디네이터가 맡고,
  PR 생성 승인 뒤 코디네이터가 PR 을 열고 정리까지 한다. 본체 세션은 머지 뒤 마무리(`task-close`) 때 돌아온다.
