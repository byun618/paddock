# bare 매핑 — 제어 런타임 없음 (iTerm2 · tmux)

능력 이름과 보장 어휘(증명/관측/공백)의 정본은 [capabilities.md](capabilities.md).

이 매핑은 **제어 런타임이 없는 환경**이다. 변형 둘을 같은 파일에 적는다 — 판정표의 공백 칸이 같기 때문이다.

| 변형 | 무엇이 다른가 |
| --- | --- |
| **iTerm2**(사람 손) | 사람이 탭을 열고 붙여 넣고 읽는다. Python API·AppleScript 로 송신·화면 읽기를 자동화할 수는 있다 |
| **tmux**(스크립트 가능) | 송신·화면 읽기·pane 목록을 셸에서 자동화할 수 있다. **보장은 늘지 않는다** — 자동화와 증명은 다른 것이다 |

## 이 매핑의 존재 이유 — 무엇이 없는지 정직하게 적는 것

**『완료 감지』가 공백이다.** 이 도구에는 "워커가 끝났다" 를 돌려주는 계약이 없다. 화면에 끝났다고 써 있는 것,
파일이 생긴 것, 프로세스가 종료한 것 — `.agents/rules/validation.md` 는 그 셋 다 완료로 치지 않는다.
따라서 **이 도구로 돌린 작업의 판정표에서 워커 완료 칸은 `공백`** 이고, 근거 칸에는
"이 도구에 『완료 감지』가 없다 — 사람이 화면을 보고 판단했다" 를 적는다. 사람의 판단은 기록되지만 증명은 아니다.

**약한 보장을 강한 보장처럼 적으면 이 매핑의 목적이 무너진다.** 이 파일에서 `증명` 은 한 칸도 없다.

## 보장 요약 (네 가지 증명 대상)

| 증명 대상 | 수준 | 근거 |
| --- | --- | --- |
| 본문이 정확히 한 번 전달됐다 | **공백** | 보낸 쪽에 ack 가 없다. iTerm2 `async_send_text` 는 "사용자가 타이핑한 것처럼" 보내고 반환값이 없다. tmux `send-keys`·`paste-buffer` 도 대상 프로그램이 읽었는지 돌려주지 않는다. 사후 확인은 『세션 기록 오라클』(관측)뿐 |
| 이 pane 이 맡긴 그 pane 이다 (세대 불변) | **관측(tmux, 조건부) / 공백(iTerm2)** | tmux pane id `%N` 은 **한 서버 수명 안에서** 변경·재사용되지 않는다. 서버가 재시작하면 재사용될 수 있고, `respawn-pane` 이면 같은 `%N` 에 다른 프로세스가 붙는다 — 그래서 `(#{pane_id}, #{pane_pid})` 쌍을 함께 기록해야 겨우 관측이 된다. iTerm2 는 `session_id` 가 있을 뿐 **세대 개념이 없다** |
| 보고가 오래된 시도에서 온 게 아니다 | **공백** | 시도(Dispatch)라는 기록 자체가 없다. 무엇이 어느 지시에 대한 응답인지 가릴 수단이 없다 |
| 사람 개입 흔적 | **관측(구분 불가)** | 사람이 직접 보는 것 자체다(H2). 화면에는 사람이 친 것과 스크립트가 보낸 것이 **같은 모양으로** 남는다 |

---

## 이 매핑이 요구하는 명령 — 선언

`capability-check runtime --tool bare` 도 이 블록을 읽는다. **대조할 광고가 없으므로 결과는 공백(exit 3)**
이지만, **블록이 없거나 비어 있거나 본문에 없는 죽은 항목이 있으면 불일치(exit 1)** 다.
"광고가 없다" 가 "아무것도 안 적어도 된다" 는 뜻은 아니다.

```required-commands
tmux new-session                    # 『세션 기동』
tmux new-window                     # 『세션 기동』
tmux send-keys                      # 『본문 주입』 — ack 없음
tmux load-buffer                    # 『본문 주입』 — 큰 본문
tmux paste-buffer                   # 『본문 주입』 — 큰 본문
tmux capture-pane                   # 『화면 관측』 — 이 도구의 유일한 관측 수단
tmux list-panes                     # 『전제 점검』·『회수·정리』 — pane_id·pane_pid 쌍
tmux kill-pane                      # 『회수·정리』
tmux kill-session                   # 『회수·정리』
async_create_tab                    # iTerm2 — 『세션 기동』
async_send_text                     # iTerm2 — 『본문 주입』 (None 을 돌려준다 = ack 없음)
async_get_screen_contents           # iTerm2 — 『화면 관측』
```

위 목록에 **『완료 감지』·『질의응답』·『제어 문맥 격리』·『준비 대기』의 명령이 하나도 없다** — 없어서 없는 것이고,
그 사실이 곧 이 매핑의 공백 칸들이다. 『세션 기록 오라클』은 `jq` 로 기록을 직접 읽는다.

## 『전제 점검』

### 명령
```bash
command -v tmux && tmux -V                       # 변형 확인
tmux list-panes -a -F '#{pane_id} #{pane_pid} #{session_name}'   # 서버 없으면 오류가 정상
ls -d /Applications/iTerm.app                    # iTerm2 변형
node .agents/harness/capability-check.mjs runtime --tool bare     # → "대조 불가" 로 끝난다
```

### 보장 수준
**공백 — 대조할 광고가 없다.** tmux·iTerm2 어느 쪽도 "내가 무엇을 보장하는가" 를 기계가 읽을 형태로 내놓지
않는다. 대조 스크립트는 이 도구에 대해 **일치도 불일치도 아닌 "대조 불가"** 로 0 이 아닌 종료를 낸다
(조용한 통과를 만들지 않는다). 그 사실이 판정표의 첫 공백이다. 확인할 수 있는 것은 **설치 여부와 버전**뿐이다.

### 상황 → 행동
- **차단 화면**: 해당 없음 — 점검이 창을 열지 않는다.
- **타임아웃·빈 결과**: `tmux list-panes` 가 "error connecting to …" 면 **서버가 없는 것**이고 오류가 정상이다.
  그것을 도구 부재로 읽지 않는다.
- **부분 실패**: 버전이 확인되는 것과 그 버전이 무엇을 보장하는지는 별개다 — 버전을 능력으로 읽지 않는다.
- **복구**: 없으면 사람이 설치한다. 이 매핑은 그 뒤에도 보장이 늘지 않는다.
- **하지 말 우회**: **"광고가 없다" 를 "요구가 충족됐다" 로 읽지 않는다.** 빈 결과는 양성 대조를 거친 뒤에야
  근거가 된다 — 여기서는 애초에 대조가 불가능하므로 공백으로 적는다.

## 『세션 기동』

### 명령
```bash
# tmux
tmux new-session -d -s <세션명> -c <작업 폴더 절대경로>
tmux new-window -t <세션명> -c <작업 폴더 절대경로>
tmux send-keys -t <대상> '<provider 실행 명령>' Enter
tmux list-panes -a -F '#{pane_id} #{pane_pid} #{pane_current_path} #{pane_current_command}'
# iTerm2 — 사람이 탭을 열고 도구를 실행한다 (Python API: iterm2.Window.async_create_tab)
```

### 보장 수준
**관측.** pane 이 생겼고 그 안에서 어떤 프로세스가 도는지는 볼 수 있다. **모델·effort·advisor 를 지정하는
제어 계층이 없으므로** provider CLI 의 플래그로 직접 지정하고, 실제로 무엇으로 해소됐는지는 배너를 읽어
관측으로 기록한다. 요청값과 관측값을 반드시 구분해 적는다.
iTerm2 쪽은 `async_create_tab` 으로 탭을 열지만 **그 탭이 무엇을 띄웠는지 돌려주지 않는다** — 확인은 화면이다.

### 상황 → 행동
- **차단 화면**: 기동 직후 화면을 읽어 trust·로그인·업데이트 화면인지 사람이 본다 — 가려낼 자동 수단이 없다.
- **타임아웃·빈 결과**: `send-keys` 는 즉시 돌아온다. provider 가 떴는지는 별도로 화면을 읽어 확인한다.
- **부분 실패**: pane 은 만들어졌는데 provider 가 안 뜬 상태가 있을 수 있다 — `#{pane_current_command}` 로 본다.
- **복구**: pane 을 버리고 새로 만든다. 남은 pane 은 사람이 센다.
- **하지 말 우회**: `send-keys` 가 exit 0 이라는 것을 "도구가 떴다" 로 읽지 않는다.

## 『준비 대기』

### 명령
```bash
tmux capture-pane -p -t <대상>            # 화면을 읽어 사람이 판단한다
# 폴링 루프를 짜도 되지만 판정 근거는 화면 문자열뿐이다
```

### 보장 수준
**공백.** "지시를 받을 수 있다" 를 돌려주는 값이 없다. 화면 문자열 일치로 짐작할 수 있을 뿐이고, 그 짐작은
**차단 화면과 준비를 가르지 못한다** — 프롬프트처럼 보이는 것이 승인 대기일 수도 있다.

### 상황 → 행동
- **차단 화면**: **사람이 읽고 사람이 치운다.** 이 도구에서는 예외 없이 그렇다.
- **타임아웃·빈 결과**: 화면이 안 바뀌는 것은 준비의 증거도 차단의 증거도 아니다.
- **부분 실패**: 해당 없음 — 대기가 사람의 판단이라 되돌릴 중간 상태가 없다.
- **복구**: 사람이 본다.
- **하지 말 우회**: 화면에 프롬프트 기호가 보인다는 이유로 주입하지 않는다 — 차단 화면 위에 본문을 넣으면
  **그 화면에 대한 대답으로 먹히고 본문이 사라진다.** 이 도구의 가장 흔한 사고다.

## 『본문 주입』

### 명령
```bash
tmux load-buffer -b <버퍼명> <본문 파일>
tmux paste-buffer -b <버퍼명> -t <대상>          # 붙여 넣기 (큰 본문)
tmux send-keys -t <대상> Enter                # 제출은 따로
# iTerm2 — 사람이 붙여 넣는다 (Python API: Session.async_send_text)
```

### 보장 수준
**공백.** 보낸 쪽에 ack 가 없다. iTerm2 `async_send_text` 는 "사용자가 타이핑한 것처럼" 넣고 아무것도 돌려주지
않는다. tmux 도 대상 프로그램이 그 바이트를 읽었는지 알려주지 않는다. **"정확히 한 번" 을 보장하는 장치가
없으므로 사람이 센다.** 판정표의 배달 칸은 `공백` 이다.

### 상황 → 행동
- **차단 화면**: 위 『준비 대기』의 사고 그대로 — 보내기 전에 반드시 화면을 읽는다.
- **타임아웃·빈 결과**: 기다릴 대상이 없다.
- **부분 실패**: 두 번 보내면 두 번 들어간다. 보낸 시각·본문·`(pane_id, pane_pid)` 를 원자료로 남기고,
  재전송 전에 화면을 읽어 이미 들어갔는지 사람이 확인한다.
- **복구**: 불확실하면 **다시 보내지 않고** 화면과 『세션 기록 오라클』을 본다.
- **하지 말 우회**: `send-keys` 로 본문과 Enter 를 한 번에 넣으면 붙여넣기 감지가 있는 provider 에서 통째로
  거절될 수 있다 — 본문과 제출을 나눈다. 그리고 **그 성공을 배달 증명으로 쓰지 않는다.**

## 『감독 워커 기동』

### 명령
```bash
# 없다. 『세션 기동』 + 『준비 대기』 + 『본문 주입』을 사람이 순서대로 하고 사람이 기록한다.
```

### 보장 수준
**공백.** 일감(Task)과 시도(Dispatch)를 묶는 기록이 없다. 무엇을 누구에게 언제 맡겼는지는 **사람이 작업 폴더
(`{{SPECS_ROOT}}/…`)에 적어야만** 남는다 — 그것이 이 도구의 유일한 원장이다.

### 상황 → 행동
- **차단 화면**: 『준비 대기』와 같다.
- **타임아웃·빈 결과**: 해당 없음 — 이 능력에 기다릴 호출이 없다(사람이 세 능력을 순서대로 한다).
- **부분 실패**: 세 단계 중 어디까지 갔는지 도구가 기억하지 않는다 — 사람이 단계마다 작업 폴더에 적는다.
- **복구**: 기록이 없으면 처음부터 다시 한다. 중복 지시가 들어갔을 가능성을 판정표에 적는다.
- **하지 말 우회**: "띄웠으니 맡겨졌다" 로 적지 않는다. 이 도구에서 워커 기동은 **사람의 기록**이다.

### 재사용 인자 규칙 (절차 문서가 가리키는 그 규칙)

**규칙이랄 것이 없다 — 그것이 이 도구의 위험이다.** tmux·iTerm2 는 "새 기동" 과 "pane 재사용" 을
구분하는 인자를 갖지 않는다. 둘 다 그냥 대상 pane 에 텍스트를 보내는 같은 명령이고, 모델·effort·advisor·
worktree 를 나중에 바꿀 수단도 없다(기동 시 명령줄에 박은 것이 끝이다).
따라서 **어느 pane 이 어떤 구성으로 떠 있는지는 사람이 남긴 기록에만 있다** — 도구에 물어볼 수 없다.
재사용하려면 그 기록을 먼저 확인하고, 없으면 재사용하지 않고 새로 띄운다.

## 『완료 감지』

### 명령
```bash
# 없다. 이 능력은 이 도구에서 공백이다.
tmux capture-pane -p -t <대상>     # 화면 읽기 — 완료 판정 근거로 쓸 수 없다
```

### 보장 수준
**공백.** 이 파일의 핵심 칸이다. 워커가 끝났다는 것을 돌려주는 계약이 없고, `validation.md` 가 대용으로 금지한
셋(TUI idle·파일 존재·exit 0)이 여기 있는 전부다.

### 판정표에 어떻게 나타나는가
- 워커 완료를 근거로 삼는 판정 항목의 **결과 칸 = `공백`**, 판정 칸 = `보류`(통과로 세지 않는다),
  근거 칸 = "이 도구에 『완료 감지』가 없다. 사람이 화면을 읽고 판단한 시각·화면 원자료를 남겼다".
- **원장 칸**은 그 관문을 실행하지 않았다면 `해당 없음 — 이유` 로 적는다(빈칸 금지).
- **실행 n/총 m 칸**은 사람이 화면을 본 회차를 그대로 적는다 — 한 번 보고 통과로 적고 나머지를 지우지 않는다.

### 상황 → 행동
- **차단 화면**: 워커가 차단 화면에서 멈춘 것과 일을 끝낸 것이 **화면으로는 비슷해 보인다.** 사람이 본다.
- **타임아웃·빈 결과**: 화면이 조용한 것은 끝난 증거가 아니다.
- **부분 실패**: 해당 없음 — 완료 감지 자체가 공백이라 부분 성공이라는 상태가 없다.
- **복구**: 없다 — 이것이 공백의 뜻이다. 사람이 pane 에 들어가 직접 확인한다.
- **하지 말 우회**: **파일이 생긴 것·프로세스가 끝난 것·`DONE.md` 가 있는 것을 완료로 적지 않는다.**
  다른 능력으로 이 공백을 메웠다고 적지 않는다.

## 『질의응답』

### 명령
```bash
# 구조화된 경로가 없다. 사람이 화면을 읽고 사람이 답을 붙여 넣는다.
tmux capture-pane -p -t <대상>
tmux send-keys -t <대상> '<답>' Enter
```

### 보장 수준
**공백.** 질문이 durable 하게 저장되지 않는다. 사람이 화면을 놓치면 질문은 사라지고, 워커는 답을 기다리며
멈춰 있다. 질문·답을 남기려면 사람이 작업 폴더에 적는다.

### 상황 → 행동
- **차단 화면**: 워커의 질문과 provider 의 차단 화면이 **화면상 구분되지 않는다.** 사람이 읽고 가른다.
- **타임아웃·빈 결과**: 대기 개념이 없다 — 사람이 주기적으로 본다.
- **부분 실패**: 답이 다른 pane 에 들어갈 수 있다. 보낼 pane 을 `(pane_id, pane_pid)` 로 확인하고 보낸다.
- **복구**: 사람이 다시 본다.
- **하지 말 우회**: 답을 여러 pane 에 뿌려 "어딘가 닿기를" 기대하지 않는다.

## 『화면 관측』

### 명령
```bash
tmux capture-pane -p -t <대상>                 # 현재 화면
tmux capture-pane -p -S -3000 -t <대상>        # 스크롤백 포함
# iTerm2 — Python API: Session.async_get_screen_contents
```

### 보장 수준
**관측 — 그리고 이 도구에서는 거의 유일한 능력이다.** 화면에는 사람이 친 것과 스크립트가 보낸 것이
**같은 모양으로** 남으므로 사람 개입 여부도 구분되지 않는다(H2).
iTerm2 는 `async_get_screen_contents` 가 같은 일을 하고, 역시 **누가 넣었는지는 돌려주지 않는다.**

### 상황 → 행동
- **차단 화면**: 이 능력으로만 본다.
- **타임아웃·빈 결과**: 스크롤백 한계를 넘어간 출력은 사라진다 — 긴 출력은 provider 가 파일로 쓰게 만든다.
- **부분 실패**: TUI 는 화면을 다시 그리므로 스크롤백이 조각으로 쌓인다. 현재 화면과 스크롤백을 구분해 적는다.
- **복구**: 사람이 pane 에 직접 들어가 본다.
- **하지 말 우회**: 화면 문자열을 『완료 감지』·『본문 주입』의 대용으로 쓰지 않는다. 이 도구에서는 그 유혹이
  가장 크고, 그래서 이 매핑이 존재한다.

## 『회수·정리』

### 명령
```bash
tmux list-panes -a -F '#{pane_id} #{pane_pid} #{session_name} #{pane_current_command}'
tmux kill-pane -t <대상>        # 사람이 소유를 확인한 뒤에만
tmux kill-session -t <세션명>
# iTerm2 — 사람이 탭을 닫는다
```

### 보장 수준
**관측(tmux, 조건부) / 공백(iTerm2).** tmux `%N` 은 한 서버 수명 안에서 재사용되지 않으므로 **같은 서버 안에서는**
`(pane_id, pane_pid)` 쌍이 맞으면 같은 pane 이라고 관측할 수 있다. 서버가 재시작했거나 `respawn-pane` 이 있었으면
그 관측은 깨진다. iTerm2 는 세대 개념이 없다.

### 상황 → 행동
- **차단 화면**: 해당 없음 — 목록·종료 명령은 pane 에 입력을 넣지 않는다(차단은 『화면 관측』이 본다).
- **타임아웃·빈 결과**: `list-panes` 가 오류면 서버가 없는 것이다 — pane 이 모두 정리됐다는 뜻은 **아니다**
  (다른 서버·소켓이 있을 수 있다).
- **부분 실패**: **H5 — 사람이 열어 준 pane 은 남는다.** 내가 만든 pane 만 닫고, 빌린 pane 은 사람에게 알린다.
  누가 만들었는지는 도구가 기억하지 않으므로 **만들 때 작업 폴더에 적어 둔 것이 유일한 근거다.**
- **복구**: 어느 pane 을 닫아야 할지 불확실하면 **닫지 않는다.** 잘못 닫은 pane 은 되돌릴 수 없다.
- **하지 말 우회**: `kill-server`·`kill-session` 으로 통째로 정리하지 않는다 — 사용자의 다른 작업이 같은 서버에
  있을 수 있다.

## 『세션 기록 오라클』

### 명령

이 도구에서는 이것이 **유일한 사후 확인 수단**이다. 그리고 **경로를 얻는 수단이 없다** —
tmux·iTerm2 는 JSON 응답을 돌려주지 않으므로 기록 경로를 응답에서 꺼낼 수 없다.
그래서 경로는 **사람이 기동 때 스스로 정해 두는 것**이 유일한 방법이다:

1. **기동할 때 세션 id 를 직접 박는다** — 예: `claude --session-id <내가 만든 UUID>`.
   그러면 H6 의 홈 경로 + 그 UUID 로 파일이 특정된다. **이것이 유일하게 증명에 가까운 경로다**
   (id 를 박지 않으면 provider 가 스스로 만들고, 그 값을 돌려받을 창구가 없다).
2. 박지 않았다면 H6 의 홈 경로에서 **cwd·시각으로 후보를 좁힌다.** 동시에 여러 세션을 띄웠으면
   **어느 파일이 그 pane 의 것인지 가릴 수 없다 — 공백이다.** 추측한 파일을 근거로 쓰지 않는다.
3. 기동 명령·시각·고른 파일 경로를 **작업 폴더에 적어 둔다.** 이 도구에서는 그 기록이 유일한 연결 고리다.

읽는 방법(`jq` 블록)은 [capabilities.md](capabilities.md) H6 에 있다 — 거기서 고른 파일 경로를 인자로 준다.

### 보장 수준
**관측.** 그리고 이 도구에서는 **배달의 유일한 사후 단서**다. 기록에 본문이 있으면 "들어갔다" 를 관측한 것이고,
없으면 배달 실패인지 기록 생략인지 가를 수 없다(H1). **사람이 붙여 넣은 경우에도 같은 모양으로 남는다** —
그래서 사람 개입 구분에는 쓸 수 없다.

### 상황 → 행동
- **차단 화면**: 해당 없음 — 기록 파일을 읽는 것뿐이라 화면을 거치지 않는다.
- **타임아웃·빈 결과**: 기록 부재는 배달 실패의 증거가 아니다.
- **부분 실패**: 같은 폴더에 세션이 여럿이면 어느 것이 이 pane 인지 가릴 수 없다 — 기동 시각으로 좁히고
  좁힌 근거를 적는다.
- **복구**: 없다. 확인 불가는 확인 불가로 적는다.
- **하지 말 우회**: 기록에 본문이 1건 있는 것을 "정확히 한 번 배달됨" 으로 승격하지 않는다 — 기록은 계약이 아니다.

## 『제어 문맥 격리』

### 명령
```bash
tmux -L <전용 소켓 이름> new-session -d -s <세션명>   # 소켓을 갈라 다른 작업과 섞이지 않게 한다
tmux -L <전용 소켓 이름> list-panes -a
```

### 보장 수준
**관측.** Run·mailbox 라는 제어 문맥 자체가 없으므로 격리할 상태도 없다. 대신 **소켓(`-L`)과 세션 이름으로
물리적으로 가른다** — 다른 작업의 pane 을 밟지 않는 것이 여기서 할 수 있는 전부다.

### 상황 → 행동
- **차단 화면**: 해당 없음 — 소켓을 갈라 새 세션을 만드는 것뿐이라 에이전트 화면을 지나지 않는다.
- **타임아웃·빈 결과**: 기다릴 제어 문맥이 없다. **빈 결과라는 개념도 없다** — 격리는 소켓 이름·세션 이름으로만 하고, 그 이름을 잘못 쓰면 조용히 남의 서버에 붙는다(그것이 이 도구의 위험이다).
- **부분 실패**: 기본 소켓(`default`)을 쓰면 사용자의 다른 tmux 작업과 같은 서버에 들어간다 — 작업 전용
  소켓 이름을 쓰고 그 이름을 작업 폴더에 적는다.
- **복구**: 섞였으면 새 소켓으로 옮기고, 남은 pane 은 사람이 센다.
- **하지 말 우회**: 사용자의 기본 서버에서 세션·pane 을 지우지 않는다.
